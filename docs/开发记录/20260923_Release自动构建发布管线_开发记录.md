# Release 自动构建发布管线 开发记录

**开发周期**: 2026-09-23
**文档创建时间**: 2026-09-23
**作者**: Leili + Claude Code
**主题**: 推送 `v*` tag 后，由 GitHub Actions 自动构建 Windows 安装包并发布到 Releases 页面，供网页直接下载

---

## 1. 背景

此前出安装包只能在本机执行 `npm run tauri build`，产物放在 `target/release/bundle/` 下，GitHub 上没有可以直接下载的地方。这次的目标是：打一个 tag，就能在仓库 Releases 页面下载到 `.msi` 和 `-setup.exe`。

## 2. 结论先行

- 流水线已上线并实测跑通：v0.3.0 构建用时 7m37s，Release 页面有两个安装包，分别是 `MirrorSync_0.3.0_x64-setup.exe` 和 `MirrorSync_0.3.0_x64_zh-CN.msi`。
- 发版流程：`npm version x.y.z --no-git-tag-version` → 提交 → `git tag vx.y.z` → `git push origin main vx.y.z`。
- 首次推送时 tag 没有触发流水线，原因是 workflow 文件和 tag 在同一次 push 里（详见 4.1）。以后 workflow 已经在仓库里，不会再遇到。

## 3. 设计决策记录

| 决策 | 选择 | 理由 |
|---|---|---|
| 触发方式 | push `v*` tag | 发版是显式动作，不和日常推 main 混在一起 |
| 版本一致性 | 第一步校验 tag 必须等于 `v` + `package.json.version`，不一致就失败 | `package.json` 是版本号唯一真源（见 `b5bb686`）。tag 与版本不一致时，安装包文件名和 Release 标题会对不上 |
| 构建平台 | 只用 `windows-latest` | 工具定位是 Windows 桌面工具，不做无用的多平台矩阵 |
| 构建与上传 | 直接用 `npm run tauri build` 构建，再用 runner 自带的 `gh release create` 上传；不用 `tauri-action` | `.cargo/config.toml` 把产物目录移到了仓库根目录 `target/`。自己写产物路径，比依赖第三方 Action 去推断路径更可控、更透明 |
| Rust 缓存 | `Swatinem/rust-cache`，`workspaces: './src-tauri -> ../target'` | 同样是因为产物目录不在 `src-tauri/target`，要显式指定 |
| 代码签名 | 不做 | 个人工具，证书成本大于收益，代价是首次运行会出现 SmartScreen 提示（README 已说明） |
| Release 说明 | `--generate-notes` 自动生成 | 零维护成本 |

## 4. 踩坑记录

### 4.1 workflow 与 tag 同一次推送，tag 没有触发流水线

- **现象**：`git push origin main v0.3.0` 推送成功。约 80 秒内查了三次 API，`actions/runs` 都返回 `total_count: 0`。但 `actions/workflows` 显示 Release workflow 已经是 `state: active`，远端 tag 也正确指向 `5f007cf`。
- **排查**：先排除了仓库私有（API 显示 `private=false`）和 workflow 未被识别这两种可能。剩下的解释是：tag 事件被处理时，这个 workflow 还没在 GitHub 那边注册好。这是根据现象推断的，没有官方文档佐证。
- **解决**：删掉远端 tag 再重推同一个 tag（`git push origin :refs/tags/v0.3.0` 后 `git push origin v0.3.0`），指向的提交不变，流水线随即触发。
- **教训**：新增 tag 触发的 workflow 时，先单独把 workflow 推到 main，再推 tag。如果已经一起推了，重推同一个 tag 即可，不需要改版本号。

### 4.2 GitHub API 附件列表滞后，误以为安装包没上传

- **现象**：流水线所有步骤显示 success，但未登录调用 `releases/tags/v0.3.0` 返回的 `assets` 为空，间隔 10 秒再查仍然为空。
- **真正原因**：用浏览器打开 Release 页面，显示 Assets 4（2 个安装包 + GitHub 自动附带的 2 个源码包），说明上传其实已经完成，是未认证 API 的数据滞后。
- **教训**：未登录时判断 Release 附件，以网页为准，不要只看 API。另外 job 日志必须登录才能查看，未登录时只能看到步骤状态和 Annotations。

### 4.3 Node.js 20 弃用警告

- **现象**：运行通过，但 Annotations 里有 1 条 warning，内容为 `Node.js 20 is deprecated... actions/checkout@v4, actions/setup-node@v4`。
- **解决**：两者都升级到当时的最新大版本 v7（`action.yml` 中均为 `using: node24`）。逐一查看了 v5、v6、v7 的破坏性变更：runner 最低版本要求、fork PR checkout 限制、自动缓存规则调整，都不影响本流水线（托管 runner、tag 触发、显式声明 `cache: npm`）。
- **验证状态**：已推送到 main，但本流水线只在推 tag 时触发，**警告是否消除要等下次发版确认**。

## 7. 给后续对话的提示

- 发版只需按 README 的四步操作，tag 与 `package.json` 版本不一致时会在第一步报错退出。
- 产物目录在仓库根目录 `target/`，不在 `src-tauri/target/`。修改 workflow 中的产物路径或缓存配置时要注意这一点。
- 本机没有安装 `gh`。未登录时，查询公开仓库的运行状态可以用 `curl https://api.github.com/repos/MonkeyDTH/MirrorSync/actions/runs`；Release 附件以网页为准（见 4.2）。
