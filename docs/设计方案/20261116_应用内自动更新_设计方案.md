# 应用内自动更新

**创建时间**: 2026-11-16 10:49
**背景**: 现在发新版后，用户只能自己去 GitHub Release 下载安装包。目标是让应用自己发现新版本，用户确认后一键完成下载、安装和重启。

---

## 1. 总体方案

使用 Tauri 官方插件 `tauri-plugin-updater`。更新清单放在 GitHub Release，用静态的 `latest.json`，不需要自建服务器。

```
发版（GitHub Actions，推 v* tag 触发）
  tauri build（注入签名私钥）
    ├─ MirrorSync_x.y.z_x64-setup.exe  + .sig
    └─ MirrorSync_x.y.z_x64_zh-CN.msi  + .sig
  scripts/release-notes.mjs   → release-notes.md   （已有，暂未提交）
  scripts/updater-manifest.mjs → latest.json        （新增）
  gh release create：安装包、latest.json 和 Release 说明一次性发布

客户端
  启动时 / 点「检查更新」
    → GET https://github.com/MonkeyDTH/MirrorSync/releases/latest/download/latest.json
    → 与当前版本比较 → 有新版本时弹窗（版本号 + 更新说明）
    → 用户点「立即更新」→ 下载并显示进度 → 用公钥校验签名
    → 启动安装程序（passive 模式）→ 应用退出 → 安装完成后安装程序自动重新打开应用
```

**选型理由**

- **官方 updater 插件**：签名校验、下载、按安装包类型选择、调起安装程序都已经实现好了，自己写只会更差。备选是自己写下载逻辑再调起安装包，需要自己做完整性校验，没有收益，所以不选。
- **清单自己用脚本生成，不换成 `tauri-apps/tauri-action`**：tauri-action 能自动生成 latest.json，但会接管整个 Release 创建流程，和已有的「tag 与版本校验」以及自定义 Release 说明（`release-notes.mjs`）冲突。生成清单只需要 40 行左右的脚本，保留现有流水线更简单。
- **不引入 `tauri-plugin-process`**：在 Windows 上，执行安装步骤时应用会被插件强制退出，安装程序默认会自动重启应用（源码 `updater.rs`：`If the Windows installer should restart the app after installed, default is true`）。前端拿不到「安装完成后调用 relaunch」的机会，所以不需要这个插件。

## 2. 详细设计

### 2.1 签名密钥（一次性准备，需要你本人操作）

```
npm run tauri signer generate -- -w %USERPROFILE%\.tauri\mirrorsync.key
```

- 生成时设置密码。生成后会得到私钥 `mirrorsync.key` 和公钥 `mirrorsync.key.pub`。
- 私钥和密码写入 GitHub Secrets：`TAURI_SIGNING_PRIVATE_KEY`（私钥文件内容）和 `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`。
- **私钥和密码要另外备份到密码管理器**。私钥丢失后，已安装的用户永远收不到更新，只能手动重装。
- 公钥内容写入 `tauri.conf.json`。公钥是公开信息，可以提交到仓库。

### 2.2 Rust 侧

`src-tauri/Cargo.toml` 新增依赖：

```toml
tauri-plugin-updater = "2"
```

`src-tauri/src/lib.rs` 注册插件：

```rust
.plugin(tauri_plugin_updater::Builder::new().build())
```

`src-tauri/capabilities/default.json` 的 permissions 追加 `"updater:default"`，其中包含 check、download、install 和 download-and-install 四个权限。

### 2.3 tauri.conf.json

```jsonc
"bundle": {
  "createUpdaterArtifacts": true,   // 构建时为 msi 和 nsis 各生成一个 .sig
  ...
},
"plugins": {
  "updater": {
    "pubkey": "<mirrorsync.key.pub 的内容>",
    "endpoints": ["https://github.com/MonkeyDTH/MirrorSync/releases/latest/download/latest.json"],
    "windows": { "installMode": "passive" }  // 只显示进度条，用户无需操作
  }
}
```

### 2.4 latest.json 与生成脚本 `scripts/updater-manifest.mjs`

输出格式：

```json
{
  "version": "0.4.0",
  "notes": "<release-notes.md 全文>",
  "pub_date": "2026-11-16T03:00:00Z",
  "platforms": {
    "windows-x86_64-nsis": { "url": ".../download/v0.4.0/MirrorSync_0.4.0_x64-setup.exe", "signature": "<.sig 内容>" },
    "windows-x86_64-msi":  { "url": ".../download/v0.4.0/MirrorSync_0.4.0_x64_zh-CN.msi", "signature": "<.sig 内容>" },
    "windows-x86_64":      { "url": "<同 nsis>", "signature": "<同 nsis>" }
  }
}
```

- 用法：`node scripts/updater-manifest.mjs <tag> <notes 文件> > latest.json`。
- 在 `target/release/bundle/{nsis,msi}/` 下用 glob 找安装包和对应的 `.sig`。找不到或数量不等于 1 时直接报错退出，避免发布一份残缺的清单。
- URL 用 `https://github.com/MonkeyDTH/MirrorSync/releases/download/<tag>/<文件名>` 拼出来。
- **为什么同时写带类型的 key 和不带类型的 key**：插件会先找 `{os}-{arch}-{安装包类型}`，再找 `{os}-{arch}`（源码 `get_urls`）。类型来自构建时写入二进制的 bundle type，所以 MSI 用户会更新到 MSI，NSIS 用户会更新到 NSIS。兜底的 key 指向 NSIS，用来应对无法识别类型的情况，例如直接运行 exe 而不是通过安装包安装的情况。

### 2.5 发布流水线 `.github/workflows/release.yml`

- 「构建安装包」步骤加上 env：`TAURI_SIGNING_PRIVATE_KEY` 和 `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`，都从 secrets 读取。
- 「生成 Release 说明」之后新增一步：`node scripts/updater-manifest.mjs "$GITHUB_REF_NAME" release-notes.md > latest.json`。
- `gh release create` 的上传列表追加 `latest.json`。
- **为什么不会出现不一致的窗口期**：`releases/latest/download/` 只指向已经发布的最新 Release。安装包和 latest.json 在同一条 `gh release create` 里一起上传，所以客户端不会读到「清单已更新但安装包还没上传」的状态。
- 依赖当前尚未提交的 Release 说明改动（`fetch-depth: 0` 和 `release-notes.mjs`），方案在这个基础上继续改。

### 2.6 前端

**`src/lib/updater.ts`**：对插件做薄封装，便于 UI 调用。

```ts
// 检查更新；silent=true 时网络错误不向上抛（启动时自动检查用）
checkUpdate(): Promise<Update | null>
```

**`src/components/UpdateDialog.tsx`**：基于现有的 `components/ui/dialog.tsx`。

- props：`update: Update | null`、`syncing: boolean`、`onClose()`。
- 显示内容：「发现新版本 vX.Y.Z（当前 vA.B.C）」，以及 `update.body`，即更新说明。说明用 `whitespace-pre-wrap` 原样显示，不渲染 Markdown，因为说明本来就是简单的分组列表，不值得为此引入渲染依赖。
- 按钮：「稍后」关闭弹窗，本次启动内不再自动提示；「立即更新」开始下载。
- 下载中：用 `Started` 事件里的 contentLength 和累计的 `Progress` 字节数显示百分比进度条。这时禁止关闭弹窗，按钮显示「正在下载…」。
- `syncing === true` 时禁用「立即更新」，并提示「同步完成后再更新」。原因是安装时应用会被强制退出，会打断正在进行的文件复制。
- 下载或安装失败时，用 toast 显示错误，并恢复按钮状态。

**`src/App.tsx`**：

- 新增 state：`update: Update | null`。
- 挂载时调用一次 `checkUpdate()`。有新版本就打开弹窗；出错时静默，只打 `console.warn`，避免离线启动时弹出报错。
- header 右侧新建按钮旁边加一个弱化的文字按钮，显示当前版本号（`getVersion()`，来自 `@tauri-apps/api/app`）和检查更新图标。点击后手动检查：有更新就弹窗；没有更新提示 `toast.success("已是最新版本")`；出错提示 `toast.error`。
- 把已有的 `syncing` 传给 `UpdateDialog`。

**前端依赖**：`@tauri-apps/plugin-updater`。

## 3. 分阶段实施计划

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| 1. 密钥 | 你生成密钥对，并配置好两个 GitHub Secrets | `gh secret list` 能看到两个 secret；私钥已备份 |
| 2. 接入与本地构建 | 完成 2.2、2.3、2.6；本地设置签名环境变量后执行 `npm run tauri build` | 产物目录下 msi 和 nsis 都有 `.sig`；`npm run tauri dev` 启动时检查不报错（线上还没有 latest.json，会静默失败）；手动检查会提示错误 |
| 3. 流水线 | 完成 2.4、2.5；本地用阶段 2 的产物运行脚本 | 生成的 latest.json 字段完整，URL 文件名与产物一致 |
| 4. 发布 v0.4.0 | 第一个带更新功能的版本，需要手动安装 | Release 中包含 latest.json；`releases/latest/download/latest.json` 可以访问 |
| 5. 端到端验证 | 发布 v0.4.1（可以是一个很小的真实改动） | 分别用 NSIS 和 MSI 安装的 v0.4.0：启动后弹窗 → 更新 → 自动重启后显示 0.4.1，并且仍是原来的安装类型（不会出现两份安装）；同步中「立即更新」不可点；断网启动没有报错弹窗 |

推荐按顺序执行：阶段 2 能确认签名链路，阶段 3 在本地就能验证脚本，不用为了试流水线反复打 tag。

## 4. 风险点

| 风险 | 说明 | 缓解 |
|---|---|---|
| 私钥丢失 | 已安装的用户再也无法自动更新 | 生成后立刻备份到密码管理器（阶段 1 的验收项） |
| 存量 v0.3.0 用户 | 旧版本没有 updater，无法自动升级 | v0.4.0 的 Release 说明里写明需要手动安装一次 |
| 更新时打断同步 | Windows 安装时应用被强制退出 | 同步中禁用「立即更新」 |
| GitHub 在国内访问不稳定 | 检查或下载失败 | 启动检查失败时静默；手动检查给出明确报错。暂不做镜像（见不纳入范围） |
| 安装包类型识别失败 | 更新时装成了另一种安装包，导致系统里出现两份 | 阶段 5 分别验证 MSI 和 NSIS 两条路径 |

## 5. 待确认决策点

1. **版本号**：首个带更新功能的版本定为 **v0.4.0**。推荐用 minor，因为这是新功能。
2. **自动检查频率**：**只在启动时检查一次**。推荐这样做，因为 MirrorSync 用完即关，不常驻，不需要定时轮询。

## 6. 不纳入本次范围

- 后台静默下载（已决定采用弹窗询问）
- 国内下载镜像或备用 endpoint
- macOS / Linux 的更新（目前只发 Windows）
- 增量更新（Tauri 不支持；安装包只有几 MB，没有必要）
- Windows 代码签名证书（是另一件事；不签名时，SmartScreen 对 passive 安装的影响在阶段 5 观察）
- 更新说明的 Markdown 渲染

### 7.1 与方案的偏差

| 方案 | 实际 | 原因 |
|---|---|---|
| 新增 `src/lib/updater.ts` 薄封装 | 没有新增，`App.tsx` 直接调用插件的 `check()` | 封装只是转发调用，没有逻辑可以收进去；启动静默和手动报错是两种调用方式，放在调用处更直观 |
| 前端依赖装最新版 `@tauri-apps/plugin-updater` | 锁定为 `~2.12.0` | 见 7.2 第 1 条 |
| 阶段 2 用正式密钥本地构建 | 用临时测试密钥（`tmp/test-sign.key`）本地构建 | 构建时只用私钥签名，不会拿公钥比对，验证产物和清单不需要正式密钥的密码；正式密钥第一次在 CI 中使用 |

### 7.2 踩的坑

1. **npm 插件版本和 Rust crate 不匹配，构建被拦下**：`npm i @tauri-apps/plugin-updater` 装了 2.14.1，它依赖 `@tauri-apps/api@^2.12`，顺带把 api 从 2.11.1 升到了 2.12.4。而 `cargo add` 受锁定的 tauri 2.11.5 限制，只能装到 updater crate 2.12.0。`tauri build` 报错：`Found version mismatched Tauri packages ... tauri (v2.11.5) : @tauri-apps/api (v2.12.4)`。修复方式是恢复 `package-lock.json`，再安装 `@tauri-apps/plugin-updater@~2.12.0`，api 回到 2.11.1。**教训：给 Tauri 加插件时，npm 包要和 crate 保持同一个小版本，不能默认装 latest。**
2. **PowerShell 下 `npm run tauri signer generate -- -w ...` 报 `No workspaces found`**：PowerShell 吞掉了 `--`，`-w` 被 npm 当成 `--workspace`；同时 `%USERPROFILE%` 在 PowerShell 里不展开。改用 `npx tauri signer generate -w "$env:USERPROFILE\.tauri\mirrorsync.key"`。
