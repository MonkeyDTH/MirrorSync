# 同步期间界面卡死修复

**创建时间**: 2026-11-16 11:35
**背景**: `sync_pairs` 是同步命令，Tauri 2 会把它放在主线程执行。同步期间窗口无法响应，进度条在同步结束前不会刷新。这个版本修复它，作为 v0.4.1 发布，同时用这次发版完成自动更新的端到端验证。

---

## 0. 代码审查结论

全部源码约 940 行，我都通读了一遍。按影响从大到小排列：

| # | 问题 | 位置 | 影响 | 本次处理 |
|---|---|---|---|---|
| 1 | **同步命令在主线程执行**。Tauri 文档原文：「Commands without the async keyword are executed on the main thread」 | `commands.rs` 中的 `sync_pairs` | 文件较多或较大时，窗口拖不动、显示「未响应」；进度面板形同虚设，因为进度事件要等主线程空闲才能送到界面，结束时一次性涌入 | ✅ 修复 |
| 2 | 每个文件都发一次进度事件，包括被跳过的文件 | `sync.rs` 的循环 | 修好 #1 之后，几万个文件的目录在一两秒内会推几万条事件，前端要连续 setState 几万次，可能出现新的卡顿 | ✅ 节流，与 #1 一起处理 |
| 3 | 遍历目录时的错误被静默丢弃（`.filter_map(\|e\| e.ok())`） | `sync.rs` 收集源文件的那一步 | 子目录没有读取权限时，其中的文件不会同步，但结果显示「同步完成」，用户不知道漏了文件 | ❓ 见第 5 节决策点 1 |
| 4 | 勾选、全选的保存失败没有处理 | `App.tsx` 中的 `togglePair` / `toggleAll` | 写配置失败时出现未捕获的 Promise 异常，界面显示已勾选，但重启后会恢复原状 | ❌ 不纳入（写配置失败极少见） |
| 5 | 包含关系判断区分大小写 | `sync.rs` 的 `starts_with` 判断 | 在 Windows 上，`D:\A` 和 `d:\a\b` 会被判断为不相关 | ❌ 不纳入（需要手动输入大小写不一致的路径才会触发，通过目录选择器选出的路径是一致的） |

## 1. 总体方案

```
改造前：前端 invoke ──► 主线程执行 sync_pair（阻塞）──► 返回
          界面冻结；进度事件排队，等主线程空闲才送达

改造后：前端 invoke ──► async 命令 ──► spawn_blocking 线程池执行 sync_pair ──► 返回
          主线程空闲，窗口正常响应；进度事件节流后实时推送（约 20 次/秒）
```

## 2. 详细设计

### 2.1 命令移出主线程（`src-tauri/src/commands.rs`）

```rust
#[tauri::command]
pub async fn sync_pairs(app: AppHandle, pair_ids: Vec<String>) -> Result<Vec<SyncResult>, String> {
    // 同步是阻塞的文件 IO，放到阻塞线程池，避免占住主线程或异步运行时的工作线程
    tauri::async_runtime::spawn_blocking(move || {
        let config = load_config(&app)?;
        Ok(pair_ids
            .iter()
            .filter_map(|id| config.pairs.iter().find(|p| &p.id == id))
            .map(|pair| sync_pair(&app, pair))
            .collect())
    })
    .await
    .map_err(|e| format!("同步任务异常退出: {e}"))?
}
```

**选型理由**：

- **选 `async fn` + `spawn_blocking`**：同步过程全是阻塞的文件 IO，`spawn_blocking` 会把它放到专门跑阻塞任务的线程池里。
- **不选 `#[tauri::command(async)]`**：它只是把同步函数包进异步任务，阻塞 IO 仍然会长时间占住异步运行时的工作线程。改动量其实一样，但前者才是正确用法。
- 参数都是拥有所有权的类型（`AppHandle`、`Vec<String>`），不受 async 命令不能用借用参数的限制。
- **只改 `sync_pairs`**：其他配置读写命令很快，留在主线程反而能保证它们按顺序执行，不会出现并发写 `config.json` 时修改相互覆盖的问题。同步命令在开始时读取一次配置快照，之后用户在同步期间编辑或删除目录对，不会影响正在进行的同步。

### 2.2 进度事件节流（`src-tauri/src/sync.rs`）

循环内只在满足以下任一条件时才 emit：

- 是第一个文件；
- 是最后一个文件（保证进度最终显示为 total/total）；
- 距离上次 emit 已经超过 50ms。

```rust
const PROGRESS_INTERVAL: Duration = Duration::from_millis(50);
let mut last_emit: Option<Instant> = None;
// 循环内：
let is_last = i + 1 == total;
if is_last || last_emit.map_or(true, |t| t.elapsed() >= PROGRESS_INTERVAL) {
    let _ = app.emit("sync-progress", ...);
    last_emit = Some(Instant::now());
}
```

50ms 约等于每秒 20 次，进度条看起来是连续变化的，事件数也和文件数脱钩了。前端不用改。

### 2.3 （待确认）遍历错误计入结果（`src-tauri/src/sync.rs`）

如果决策点 1 选「纳入」：遍历时遇到的 `walkdir::Error` 不再丢弃，而是转成 `读取失败 {路径}: {原因}` 写进 `result.errors`。前端已经支持显示错误列表并给出「部分目录对存在错误」的提示，所以不用改。

## 4. 风险点

| 风险 | 说明 | 缓解 |
|---|---|---|
| 同步期间可以编辑配置 | 主线程空出来以后，用户在同步中也能编辑或删除目录对 | 同步使用开始时读取的配置快照，不受影响；编辑本身也是安全的 |
| 重复触发同步 | 主线程不再阻塞，理论上可以再次点击「开始同步」 | 前端在 `syncing` 时已经禁用了按钮 |
| 同步中途关闭窗口 | 以前窗口卡死时关不掉，修复后可以正常关闭，进程退出会中断正在进行的复制 | 和以前强制结束进程的后果一样，最多留下一个复制了一半的文件，下次同步时会因为大小不同而重新复制。不额外处理 |

## 7. 实施结果（2026-11-16）

**提交**：`839d9b8`（窗口无响应）、`a9c31d3`（遍历错误）、`40163fd`（版本号升至 0.4.1），作为 v0.4.1 发布。决策点 1 选择纳入。

### 7.1 与方案的偏差

| 方案 | 实际 | 原因 |
|---|---|---|
| 第 0 节 #1 认为「进度条要等同步结束才刷新」 | **这个判断是错的**。基线测试中进度一直在更新（60 → 3460 → 9321 → 18608…），真正的问题只有窗口无响应 | 同步本身就在主线程上执行，`emit` 直接在主线程把事件送进 WebView，不需要排队。修复方向不受影响 |
| 遍历错误信息直接使用 walkdir 的 `{e}` | 优先取 `e.io_error()` | walkdir 的 Display 会再带一遍路径，还会出现英文前缀（`IO error for operation on ...`）。修改后是 `读取失败 <路径>: 拒绝访问。 (os error 5)` |

### 7.2 实测数据

测试数据：2 万个 1KB 小文件加 1 个 1GB 文件，测试脚本在 `tmp/perf/`。用 CDP 点击「开始同步」，每 300ms 采样一次页面进度；同时每 300ms 用 `IsHungAppWindow` 检测窗口是否无响应。

| 场景 | v0.4.0 | v0.4.1 |
|---|---|---|
| 全量复制：窗口无响应采样 | 41/56、68/83（同步开始约 4.7 秒后持续无响应，直到结束） | 0/53、0/64 |
| 全量复制：耗时 | 17.8s、26.2s | 16.8s、19.9s（磁盘波动较大，不作为结论） |
| 全部跳过：耗时 | 998ms、1003ms、1077ms | 798ms、859ms、851ms（约快 17%，来自进度节流） |
| 子目录无读取权限 | 没有报错，显示「同步完成」 | 报出 `读取失败 …\locked: 拒绝访问。 (os error 5)` |

### 7.3 踩的坑

1. **用环境变量开启 WebView2 远程调试不生效**：`WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9222` 启动后端口没有监听。查看 msedgewebview2 的命令行，只有 Tauri 自己传入的 `--disable-features=msWebOOUI,msPdfOOUI,msSmartScreenProtection`，环境变量被覆盖了。改为构建时用 `tauri build --no-bundle --config tmp/perf/debug-config.json` 临时设置窗口的 `additionalBrowserArgs`，不改仓库里的配置文件。
2. **从 Git Bash 启动时，ACL 的拒绝规则不生效**：同一个无权限目录，从 PowerShell 启动的应用会报「拒绝访问」，从 Bash 启动的应用却把文件复制了过去。`whoami /priv` 显示 Bash 进程中 `SeBackupPrivilege` / `SeRestorePrivilege` 是 **Enabled**（MSYS2 运行时在管理员权限下会主动启用），PowerShell 中是 Disabled。子进程继承这个特权后，打开目录时会绕过 ACL。**教训：涉及权限的测试不要从 Git Bash 启动被测程序。**
3. 采样脚本第一版用 `/(\d+)\/(\d+)/` 匹配整个页面，结果抓到的是顶部「已选 1/1」的勾选计数，不是进度。改为只在「同步日志」面板里匹配。
